## Context

当前页面的视觉 token 和组件样式集中在 `src/styles/global.css`，Tailwind 配置将 CSS 变量映射到页面 utility；但页面仍大量使用 candy、mango、lime、aqua、bubble 等高饱和语义和玻璃质感。共享组件、布局和工具页还存在局部样式，因此需要一次以设计 token 为中心、覆盖页面入口的统一改造。具体动机与行为契约见 `proposal.md` 和 `specs/theme-styling/spec.md`。

## Goals / Non-Goals

**Goals:**

- 建立纸、墨、灰阶、朱砂、靛青、黛绿等语义化视觉 token，并让浅色/深色主题各自拥有完整值。
- 通过共享 token 和组件样式统一首页、博客列表、博客详情、关于页、工具页、Header、Footer 的视觉表现。
- 在保留现有路由、内容渲染、主题切换和工具行为的前提下，降低页面间的视觉分叉。
- 保持中文长文阅读、代码块、表单控件、链接和状态消息的可读性与可访问对比度。
- 不依赖远程图片、外部字体、前端框架或新的运行时包来模拟水墨效果。

**Non-Goals:**

- 不重写页面信息架构、文章内容、frontmatter schema、路由或 Cloudflare 部署方式。
- 不新增文章搜索、标签筛选、动画系统或服务端功能。
- 不把页面改成仿古书法站；标题和正文仍以现代可读排版为优先。
- 不修改主题初始化和 `localStorage` 持久化逻辑，只调整主题下的视觉 token 与组件呈现。

## Decisions

### 1. 以语义 token 替换现有糖果色 token

将 Tailwind 与全局 CSS 中的颜色命名迁移到表达用途而非装饰色的 token，例如 `paper`、`paper-deep`、`ink`、`ink-muted`、`cinnabar`、`indigo`、`jade` 和 `wash`。同步迁移源码中的 `bg-candy`、`bg-mango` 等旧 utility 使用，避免保留语义错误的颜色别名。

浅色主题以宣纸、暖灰、浓墨和少量朱砂/靛青为主；深色主题以墨黑、黛灰、浅纸色文字和低亮度点缀色为主。已有 shadow token 保留用途，但调整为更短、更柔和、更少发光的阴影。

**替代方案**：只改变旧 token 的 CSS 值而不改名字，改动较少，但会让 `candy`、`mango` 等名称继续误导后续维护者；不采用。

### 2. 用低透明度 CSS 洗染取代高饱和渐变和玻璃效果

在 `global.css` 中用少量线性/径向渐变模拟纸面晕染、墨迹扩散和局部色块；透明度保持克制，纹理只作为背景层。`surface-card`、`hero-shell`、工具卡片和按钮使用实色或轻微半透明表面、细边框和柔和阴影，移除造成强烈玻璃感的高饱和光泽组合。

背景纹理通过伪元素或背景图层实现，不新增图片资源；必须设置 `pointer-events: none` 和合适的层级，不能遮挡内容或影响交互。

**替代方案**：引入水墨纹理图片或第三方背景库，视觉可控性更强但增加资源体积、版权和响应式适配成本；不采用。

### 3. 共享组件先行，页面局部样式随后迁移

先更新 `BaseHead` 所加载的全局样式、Header、Footer、BlogPost 布局和主题相关控件，再迁移首页、博客列表、关于页和工具页的显式颜色 class。这样所有页面先获得一致的基础 token，再处理页面特有的 hero、卡片、CTA、工具输入框和结果状态。

工具页的 `.tool-*` 样式继续保留在 `src/pages/tools.astro`，但颜色、边框、阴影和焦点状态只引用共享语义变量；跨页面重复的视觉规则提升到 `global.css`。

**替代方案**：每个页面单独重写完整样式，短期更直观但会扩大重复规则和主题分叉；不采用。

### 4. 保留主题机制，只替换主题值和视觉适配

继续使用 `data-theme="dark"`、`BaseHead.astro` 的无闪烁初始化和 `src/components/theme.ts` 的切换持久化。所有主题差异集中在 CSS token 和 `[data-theme="dark"]` 规则中，组件不新增第二套主题状态。

深色主题的水墨表达使用更深的墨色底、黛灰表面和低亮度朱砂/靛青；浅色主题使用暖宣纸底和浓淡墨色。按钮、链接、active 状态、错误/成功消息在两个主题中都必须有非颜色区分，例如边框、文字或图标变化。

**替代方案**：通过 JavaScript 动态替换 class 管理整套配色，状态复杂且可能引入闪烁；不采用。

### 5. 保持现有字体资产并补充稳定的中文系统回退

继续 preload 和使用 `public/fonts/` 中的 Atkinson 字体，拉丁字符保持现有字形；中文标题和正文通过稳定的系统中文/衬线回退字体获得适合水墨主题的字形，不下载新的远程字体。标题可以使用更明确的字重和留白表达层级，但不使用难以阅读的书法字体作为正文。

## Risks / Trade-offs

- **[Risk]** 暖灰或低饱和颜色导致正文、链接或控件对比度不足。→ 为正文和交互状态设定明确的对比度检查，浅色和深色都验证至少 4.5:1 文本、3:1 交互元素。
- **[Risk]** 旧 utility class 迁移不完整，导致个别页面仍显示旧糖果色。→ 在迁移后搜索旧 token 名称，逐页检查所有主路由，并以 `npm run check` 验证构建。
- **[Risk]** CSS 洗染或 backdrop-filter 影响性能、可读性或点击区域。→ 只在背景层使用低成本渐变，禁止纹理层接收指针事件，并在窄屏和低性能浏览器中检查。
- **[Risk]** 不同系统的中文字体回退差异造成标题换行变化。→ 使用明确的字体栈和现有响应式断点，检查 Windows 浏览器的首页、文章详情和工具页换行。
- **[Risk]** 工具页状态样式被全局 token 改动误伤。→ 保留错误、成功、焦点和只读状态的独立边框/文字规则，逐项执行工具页交互检查。
- **[Trade-off]** 不引入真实水墨图片或字体，能降低依赖和加载成本，但纹理表现会更抽象。→ 将识别度放在颜色、留白、边界、层次和克制的 CSS 洗染上，而不是追求写实纹理。

## Migration Plan

1. 更新全局语义颜色、阴影、背景和 Tailwind 映射，建立浅色/深色 token。
2. 迁移共享组件和 `BlogPost` 布局，确保导航、主题切换、文章正文和页脚先完成双主题适配。
3. 按首页、博客列表、关于页、工具页顺序迁移页面 utility class 与局部样式，清理旧糖果色 token 引用。
4. 运行 `npm run check`，在开发/预览环境检查 `/`、`/blog`、一篇文章、`/about`、`/tools` 的浅色、深色、移动端和桌面端。
5. 这是纯前端视觉迁移，无数据迁移和 API 迁移；若发布后出现严重视觉回归，回滚本次源码与样式变更即可，不影响文章数据或 Worker 配置。
